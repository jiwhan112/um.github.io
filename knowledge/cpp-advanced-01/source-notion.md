## 1. 절차 지향과 객체 지향을 다시 구분하기

절차 지향은 함수를 쓰지 않거나 모든 코드를 한 파일에 작성한다는 뜻이 아닙니다. 데이터를 어떤 순서의 연산으로 처리할지에 중심을 두는 방식입니다. 객체 지향은 객체의 상태와 그 상태를 다루는 연산, 객체 사이의 계약을 중심으로 프로그램을 조직합니다. 두 방식을 적대적인 선택지로 볼 필요는 없습니다. 게임에서는 데이터 구조와 자유 함수로 표현하는 계산, 수명을 관리하는 클래스, 가상 인터페이스와 템플릿이 함께 쓰일 수 있습니다.

클래스를 많이 만들거나 모든 함수에 Getter/Setter를 붙였다고 설계가 좋아지지는 않습니다. 중요한 것은 <b>사용자가 잘못된 상태를 만들기 어렵고, 내부 표현이 바뀌어도 호출하는 코드가 덜 바뀌는가</b>입니다.

## 2. struct와 class의 실제 차이

C++의 struct와 class는 모두 멤버 함수, 생성자, 소멸자, 상속, 가상 함수를 가질 수 있습니다. 기본 멤버 접근과 기본 상속 접근이 다릅니다. struct는 public, class는 private가 기본입니다. struct는 무조건 데이터만, class는 무조건 함수를 가져야 한다는 것은 언어 규칙이 아닙니다.

서로 독립적인 값을 묶는 <code>Point</code> 같은 타입은 공개 멤버의 단순 구조체가 읽기 좋을 수 있습니다. 반면 <code>0 ≤ 현재 체력 ≤ 최대 체력</code>을 항상 유지해야 한다면 임의 대입보다 의미 있는 연산을 제공하는 편이 낫습니다.

```c++
struct Point { float x{}; float y{}; };

class Health {
    int maximum_;
    int current_;
public:
    explicit Health(int maximum)
        : maximum_(maximum), current_(maximum) {
        if (maximum <= 0)
            throw std::invalid_argument("maximum must be positive");
    }
    int Current() const noexcept { return current_; }
    void Damage(int amount) {
        if (amount < 0)
            throw std::invalid_argument("negative damage");
        current_ = amount >= current_ ? 0 : current_ - amount;
    }
};
```

위는 <code><stdexcept></code>가 필요한 발췌 코드입니다. 전체 클래스와 main, 회복·경계 테스트는 실습 파일에 있습니다. 먼저 피해량을 비교한 뒤 빼므로 과도한 피해에서도 현재 체력이 음수가 되지 않습니다. 여기처럼 두 값이 모두 음이 아닌 int라는 전제가 지켜지면 단순 뺄셈 자체는 int 범위 안에 있지만, 음수 체력을 허용하지 않는 불변식은 별도로 지켜야 합니다. 부호 없는 체력의 뺄셈이나 회복량을 먼저 더하는 구현은 래핑·오버플로 조건이 달라지므로 타입과 연산을 함께 확인합니다.

<b>불변식(invariant)</b>은 생성에 성공한 객체가 외부 연산 전후에 유지해야 하는 조건입니다. 여기서는 최대 체력이 양수이고 현재 체력이 그 범위 안에 있다는 것입니다. <code>SetCurrent(int)</code>로 아무 숫자나 받기보다는 <code>Damage</code>, <code>Heal</code>처럼 규칙을 지키는 연산을 둡니다.

## 3. 생성자는 할당 명령이 아니다

<code>Health player{100};</code>는 객체 정의이고, <code>auto p = std::make_unique<Health>(100);</code>는 동적 객체를 소유하는 스마트 포인터를 만듭니다. 생성자는 객체의 초기화를 담당하며 메모리 확보와 같은 말이 아닙니다. new 표현식은 저장 공간 확보와 초기화를 조합하지만, 자동 객체나 이미 확보된 저장 공간에서도 생성자가 실행될 수 있습니다.

초기화 목록은 생성자 본문에 들어가기 전에 멤버를 초기화합니다. 본문에서 값을 넣으면 먼저 이루어진 초기화 다음에 대입하는 경우가 됩니다. const·참조 멤버, 기본 생성자가 없는 멤버는 이 차이가 특히 중요합니다. 클래스 내부 기본 멤버 초기화도 활용할 수 있습니다.

생성자의 본문에서 실패하면 완성된 객체를 반환하지 않습니다. 예외를 사용하지 않는 프로젝트에서는 생성 팩토리가 결과와 오류를 반환하게 하거나 유효 상태를 명시적으로 설계해야 합니다. 무조건 <code>Initialize()</code>를 나누는 것이 C++ 규칙은 아닙니다. 두 단계 초기화가 필요하다면 초기화 전 객체에 어떤 함수를 호출할 수 있는지까지 정해야 합니다.

## 4. 초기화 순서는 선언이 정한다

일반적인 비위임 생성자에서는 가상 기본 클래스, 직접 기본 클래스, <b>멤버 선언 순서</b>, 생성자 본문 순으로 초기화합니다. 가상 기본 클래스 초기화는 가장 파생된 클래스가 담당합니다. 초기화 목록에 멤버 이름을 거꾸로 써도 선언 순서는 바뀌지 않습니다.

```mermaid
flowchart LR
    B["기본 클래스 생성"] --> M1["첫 번째 멤버 생성"]
    M1 --> M2["두 번째 멤버 생성"]
    M2 --> D["파생 클래스 생성자 본문"]
    D --> USE["완성된 객체 사용"]
    USE --> DD["파생 소멸자 본문"]
    DD --> R2["두 번째 멤버 소멸"]
    R2 --> R1["첫 번째 멤버 소멸"]
    R1 --> BB["기본 클래스 소멸"]
```

다이어그램은 이 실습처럼 가상 기본 클래스가 없는 경우입니다. 여러 부모·가상 상속이 있으면 그 부분을 추가해서 읽습니다. 소멸은 생성의 반대 순서를 따르지만 <b>소멸자 본문과 멤버 소멸 시점을 구분</b>해야 합니다. 파생 소멸자 본문이 먼저 실행되고 그 뒤 멤버, 기반 부분이 해체됩니다.

실습은 이벤트를 숫자로 기록합니다. 정상 생성은 <code>1,2,3,4</code>, 소멸을 포함하면 <code>1,2,3,4,-4,-3,-2,-1</code>입니다. 두 번째 멤버 생성자가 실패하면 <code>1,2,3,-2,-1</code>입니다. 실패한 멤버와 완성되지 않은 전체 객체의 소멸자는 호출되지 않고, 이미 완성된 하위 객체는 정리됩니다. 그래서 자원을 멤버 RAII 객체로 잡아두는 것이 중요합니다.

## 5. const, static, this를 서로 다른 축으로 이해하기

<code>int Current() const</code>는 이 객체를 const 경로로 사용하는 멤버 함수입니다. 보통의 비mutable 멤버를 이 경로로 수정하지 못합니다. 함수 내부 지역 변수 사용이나 다른 비const 객체에 대한 연산까지 모두 금지하는 것은 아닙니다. 포인터 멤버가 가리키는 외부 객체까지 자동으로 불변이 되는 것도 아닙니다.

<code>mutable</code>은 논리적인 관찰 연산에서 캐시 등 일부 내부 상태를 변경하도록 허용합니다. <b>스레드 안전성을 제공하는 키워드는 아닙니다.</b> 여러 스레드가 같은 캐시를 갱신한다면 별도 동기화가 필요합니다.

비정적 멤버 함수에는 대상 객체를 가리키는 this가 있습니다. 정적 멤버 함수에는 this가 없으므로 특정 객체의 멤버를 쓰려면 객체를 명시적으로 받아야 합니다. 초기화 시점이 달라서 일반 멤버를 못 쓰는 것이라는 설명은 부정확합니다. 정적 데이터 멤버는 개별 인스턴스의 멤버가 아니라 클래스 차원에서 공유되는 객체입니다. C++17의 inline static 멤버와 이전 표준의 클래스 밖 정의 방식을 구분합니다.

## 6. 접근 제어와 파일 분리

private는 해당 클래스의 멤버와 friend에서 접근할 수 있고, protected는 파생 클래스에 추가 접근을 허용합니다. protected 데이터를 많이 노출하면 파생 클래스와 내부 표현의 결합이 커집니다. friend는 항상 나쁜 것도, 캡슐화를 자동으로 잘 지키는 것도 아닙니다. 접근을 허용할 대상을 좁게 지정하는 수단으로 판단합니다.

클래스 하나당 헤더 하나와 cpp 하나는 프로젝트 관례이지 언어 요구사항은 아닙니다. 관련된 작은 타입은 함께 둘 수 있고 템플릿은 정의가 사용 지점에 보여야 하는 경우가 많습니다. public 헤더는 자기 자신이 필요한 선언을 제공하도록 만들며 우연히 다른 헤더가 먼저 include되었다는 사실에 의존하지 않습니다. 전방 선언만으로 가능한 포인터·참조 선언과 완전한 타입이 필요한 값 멤버·sizeof·삭제 등을 구별합니다.
