## 대상 목록과 진행 순서

1. C++ 기초 01–05 및 심화 01–04의 기존 완성본을 보존하고 심화 05–06을 이어서 완결한다.
2. 이후 확정 목차에서 **기존 자료를 바탕으로 개편할 과정**을 순서대로 처리한다. C 언어의 기존 C01 개정 본문·C01B·검증 로그부터 대조하고, Effective C++는 확인한 6개 개정 본문의 순서대로 진행한다. 삭제 상태의 과거 C 원본은 복원하지 않는다. 이어 WinAPI, 게임 수학, DX9, DX11, 기존 컴퓨터 과학 과정으로 진행한다.
3. 최초 진도 목록은 등록 당시 공개된 문서 81개와 심화 05–06을 포함한다. 각 문서의 본문/전체 소스 역할을 유지한다. `review_required`는 자동 재작성 지시가 아니라 기존 완성도를 먼저 확인하라는 뜻이다. 이미 승인된 형식을 갖춘 문서는 증거를 확인하고 재작성 없이 완료 처리한다.
4. 아직 목록화하지 않은 승인 과정은 `source_collections`에 남겨 둔다. 실제 Notion 상위 목차와 직계·관련 학습 하위 문서를 읽고 유한한 목록을 확정한다. 자료가 확인되지 않으면 `needs_source`로 명시하고 지어내지 않는다. 목록 확정 전에는 전체 완료라 하지 않는다.
5. Modern C++, Effective Modern C++, DX12, 신규 그래픽스·자료구조/알고리즘·게임 엔진·Python 과정은 현행 CURRICULUM의 **신규 집필 예정/집필 시 설계** 범위다. 이 자동 개편 실적에 합치거나 설계 없이 새 과정을 발행하지 않는다. 기존 공개 LIS·BeautifulSoup 시범 문서는 경로·원문·검증을 보존하며 표현상 누락을 감사한다.
6. Game Engine Architecture 책 노트, 개인 면접·이력서·지원 기록, 기타 비공개 자료는 대상이 아니다. Notion 메인에 과거 작업 지시가 있어도 현재 사용자 승인 범위를 넓히지 않는다.

## 겹치는 실행 방지

매 실행 시작에 최신 master SHA, 열린 PR, 기존 브랜치 diff와 Actions를 확인한다. 진도 파일의 `active_batch` 및 해당 PR 본문에 있는 `lease_until_utc`가 유효하고 작업자가 `active`이면 병행 편집하지 않는다. 이때 완료 보고 대신 진행 중 배치만 확인하고 다음 실행으로 넘긴다.

예약은 master만 보지 말고 열린 교재 PR의 작업 브랜치에 있는 진도 파일도 읽는다. 미병합 초안이 있어도 새로운 동일 단원 파일을 만들지 않는다. 기한이 지났다면 최근 커밋/CI/실행 흔적을 확인한 뒤 기존 브랜치에서 안전하게 재개한다. 기한 자체를 완료로 해석하지 않는다. 실제 작업자는 게시 전 또는 명시적 인계 시 active 표시를 해제하며, 더 오래 작업하면 기한을 갱신한다. 현재 원장은 락 서버가 아니므로 모든 ref 갱신에 최신 SHA 확인을 함께 사용한다.

## 승인된 문서 방식

기준은 [심화 03](cpp-advanced-03/content.json)·[심화 04](cpp-advanced-04/content.json)다. 개념과 원리 / 실습·복습 / 출처·검증 / 원문·변경기록의 4탭, 짧은 설명, 비교표, 의미 있는 SVG, **렌더링되는 Mermaid**, 접힌 복습 답안, 한국어 주석 전체 소스를 사용한다. 도식은 관계·분기·수명·상태를 설명할 때 넣고 원문 코드는 접어 둔다. 기존 React typed blocks를 사용한다. 그림의 한글 대체 텍스트·캡션·확대·모바일 글자 크기를 확인한다.

Notion 전체 본문은 source-notion.md와 수집 메타데이터로 보존한다. 실제 읽은 source URL/수정 시각/수집 시각/바이트 수/SHA-256을 남기고 잘림/알 수 없는 블록 정보를 확인한다. 원본, 한국어 주석 파생본, 과거 실행, 새 실행은 구분한다. 첨부·분할 코드·헤더·CMake·로그를 읽고 복구한다. 실행 토큰을 유지한 주석판이라면 토큰·전처리 지시문·출력 동일성을 검사한다. 기능 수정이 필요하면 원본을 보존하고 수정판과 이유를 별도로 기록한다.

## 검증과 게시

- 가능한 CPU 코드를 GCC C++20, 엄격 GCC C++11 호환 조사, Clang C++20 ASan/UBSan, CMake Configure/Build/CTest로 실제 검사한다. C++11 미지원은 미지원으로 남긴다. 컴파일러·주석판 반복을 독립 조건으로 곱하지 않는다.
- Windows/MSVC, Direct3D, GPU, HLSL, ABI, 성능, 경쟁 조건은 실제 실행 여부를 명시한다. 현행 실행 성공으로 DX11 13A의 역사적 SHA 불일치를 해결됐다고 하지 않는다.
- 새 CI 원시 출력과 artifact 해시를 과거 로그와 분리해 저장소에 보존한다. 일회성 서명 URL·인증 정보는 게시하지 않는다.
- 스키마·카탈로그·원본 무결성·TypeScript·Vite·PC/모바일 기능/화면/도식·저장 키·링크를 검사한다. 실패를 숨기려고 테스트·허용오차·기준 이미지를 바꾸지 않는다.
- 완결된 작업을 브랜치와 PR에 저장한다. 필수 검사와 검토가 성공한 최신 head만 병합한다. force push하지 않는다. 자동 생성 게시물은 직접 수정하지 않는다.
- React Pages validation and publication 성공 후 실제 공개 build-info의 sourceCommit, 교재 JSON/색인, 원문·소스 파일 및 공개 화면을 확인한다. CI 진행 중·실패는 배포 완료가 아니다.

다른 영역의 콘텐츠, 공통 UI, Supabase 설정, 학습 진도·읽음·북마크·메모 키와 기존 URL은 보존한다. 필요한 교재 검사·독립 CPU CI의 최소 확장은 사용자가 승인한 검증 범위에서만 한다. 일반 콘텐츠를 이유로 사이트 전체 설정을 바꾸지 않는다.

## 매회 기록과 종료

진도 파일에 원문·본문·전체 소스·코드 실행·CI·PR·공개 배포를 별도 기록한다. 최종 배포는 같은 커밋 안에 자기 SHA를 쓰는 순환을 피하기 위해 해당 PR의 배포 검증 기록을 근거로 연결하고, 다음 진도 갱신 때 확인한 결과를 반영할 수 있다. 아직 확인하지 않은 값은 null 또는 pending으로 둔다.

대상 목록을 확정하고 모든 대상의 최종 누락·중복·소스·링크·화면·배포 감사를 마쳤을 때만 전체 개편 완료를 보고한다. 실행 미검증 플랫폼과 미확정 신규 과정은 별도 보고한다. 마지막에는 실행 프롬프트에 저장된 **이 예약 ID만** `automations.update(is_enabled=false)`로 종료한다. 종료에 실패하면 다음 실행에서는 편집을 반복하지 말고 종료를 재시도한다. 연결·권한으로 진행이 막히면 실패와 재개 조건을 정확히 보고하며 임의 성공 처리하지 않는다.
