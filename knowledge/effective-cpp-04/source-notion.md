## 항목 32. public 상속과 대체 가능성

기반 타입으로 사용하는 코드가 기대하는 조건을 파생 타입도 지켜야 합니다. 부모 연산의 허용 입력을 파생 타입이 몰래 좁히거나 결과 의미를 바꾸면, 문법적으로 변환 가능해도 설계상 대체하기 어렵습니다. ‘현실에서 비슷하니까 상속한다’보다 프로그램 안의 계약을 먼저 봅니다.

예를 들어 저장소 인터페이스가 삭제를 허용하는데 파생 타입은 삭제가 불가능하다면, 어떤 타입으로 사용할 수 있어야 하는지를 다시 설계해야 합니다. 게임의 오브젝트 계층에서도 보이지 않는 객체에 Draw 계약을 강제하는지, 데이터만 필요한 곳에 생명주기 인터페이스가 끼어 있는지 살펴봅니다. 함수 구현을 재사용하려는 목적이라면 합성이 더 단순할 수 있습니다.

## 항목 33. 이름 가림과 using

파생 클래스에서 같은 이름을 선언하면 기본 클래스의 여러 오버로드가 이름 탐색에서 가려질 수 있습니다. 이는 virtual 여부만으로 결정되는 현상이 아닙니다. 필요한 기반 오버로드는 <code>using Base::Function;</code>으로 다시 노출하거나 별도 전달 함수를 제공할 수 있습니다.

```c++
struct Base { void Set(int); void Set(double); };
struct Derived : Base {
    using Base::Set;
    void Set(const std::string&);
};
```

이름을 노출하는 접근 권한과 실제 계약이 맞는지 확인합니다. private 상속을 쓰면서 기반 전체 기능을 무심코 공개하면 원래 숨기려던 관계가 드러날 수 있습니다. 타입에 의미 있는 기능만 전달하는 방법도 있습니다. 실습 AddOverload는 기반 int 오버로드와 파생 string 오버로드를 모두 호출합니다.

## 항목 34. 인터페이스와 기본 구현을 분리하기

순수 가상 함수는 파생 타입이 구현해야 하는 계약을 표현할 수 있습니다. 일반 가상 함수는 기본 구현을 제공하면서 재정의를 허용할 수 있고, 비가상 함수는 공통 동작을 그대로 제공하는 데 적합할 수 있습니다. 이것은 반드시 따를 수학적 분류가 아니라 어떤 변경을 허용하는지 설명하는 설계 도구입니다.

순수 가상 함수도 클래스 밖 정의를 가질 수 있습니다. 순수 가상 소멸자는 기반 소멸 과정에서 필요하므로 정의해야 합니다. 추상 클래스를 만들 수 없는 이유를 메모리 크기를 모른다는 말로 설명하지 않습니다. 비가상 함수가 public인데 파생에서 같은 이름으로 다른 의미를 주면, 사용자의 정적 타입에 따라 다른 동작을 보게 될 수 있습니다.

## 항목 35. 가상 함수 이외의 변경 지점

NVI는 비가상 공개 함수가 입력 검사·전후 작업을 담당하고, 달라지는 계산만 private 또는 protected 가상 함수로 위임하는 방식입니다. Strategy는 알고리즘 객체를 별도로 선택하게 합니다. 템플릿은 타입을 컴파일 시점에 정하는 경우, 함수 포인터·std::function은 호출 가능한 동작을 전달하거나 저장하는 경우의 선택지입니다.

```mermaid
flowchart LR
    C["호출자"] --> A["공개 Apply: 검증·공통 규칙"]
    A --> H["ApplyImpl: 변경되는 계산"]
    H --> R["결과 반환"]
```

실습 HalfDamage는 입력 범위를 공통 검사한 다음 절반 피해를 계산합니다. 어떤 방식을 써도 대상·캡처의 수명과 할당 비용, 코드 크기, 호출 비용을 확인해야 합니다. 모든 가상 함수를 std::function으로 바꿨다고 자동으로 느슨하게 결합되거나 더 빨라지는 것은 아닙니다.

## 항목 36. 비가상 함수를 다른 계약으로 가리지 않기

기반 포인터·참조로 호출하는 코드와 구체 타입으로 호출하는 코드가 비가상 이름 가림 때문에 서로 다른 동작을 보면 이해가 어려워집니다. 의도적으로 다른 이름을 쓰거나, 같은 확장 계약이면 virtual을 사용하거나, 서로 다른 타입 관계를 합성으로 표현하는 편이 명확할 수 있습니다.

비가상 함수에도 오버로드·별도 도우미 등 정상적인 사용이 있습니다. 이 항목은 ‘파생에 같은 철자가 등장하면 모두 불법’이라는 언어 규칙이 아니라 public 계약을 깨는 재정의처럼 보이는 설계를 주의하라는 조언입니다.

## 항목 37. 가상 호출의 기본 인수는 정적 선언에서

기본 인수는 호출 위치에서 보이는 선언으로 결정되고, virtual 함수의 최종 구현은 동적 타입에 따라 선택됩니다. 두 선택 과정이 다르므로 기본 타입의 default=2와 파생 타입의 default=3이 서로 다른 결과를 낼 수 있습니다.

```c++
struct Base {
    virtual ~Base() = default;
    virtual int Strength(int scale = 2) const { return scale; }
};
struct Fire : Base {
    int Strength(int scale = 3) const override { return scale * 10; }
};
```

설명용 축약 예에서 Base 참조를 통한 인수 생략 호출은 20, Fire 표현식은 30이 됩니다. 실제 테스트 Effect/Fire에서도 확인합니다. 기본값을 공통 비가상 래퍼에 모으고 내부 가상 함수에는 명시적으로 인수를 전달하는 방식으로 혼동을 줄일 수 있습니다.

근거: [N4861 — 기본 인수](https://timsong-cpp.github.io/cppwp/n4861/dcl.fct.default), [가상 함수](https://timsong-cpp.github.io/cppwp/n4861/class.virtual).

## 항목 38. 합성은 포함 관계와 구현 재사용

클래스가 다른 타입을 멤버로 포함하면 수명과 연산을 조합할 수 있습니다. Player가 Inventory를 포함하는 것과 Player가 Inventory라는 public 상속 관계는 의미가 다릅니다. 내부 구현을 위해 vector를 이용하는 타입도 vector에서 상속할 필요는 없습니다.

합성도 소유 방식에 따라 의미가 다릅니다. 값 멤버는 포함된 객체의 수명과 함께하고, 포인터 멤버는 동적 소유나 외부 관찰일 수 있습니다. 단순한 has-a 화살표 하나에 이 차이를 숨기지 않습니다. 외부에 내부 컨테이너 참조를 넓게 노출하면 합성을 써도 결합도가 커질 수 있습니다.

## 항목 39. private 상속은 제한된 구현 선택

private 상속은 public 대체 관계를 외부에 제공하지 않으면서 기반의 구현·protected 접근·가상 확장 지점을 활용하는 경우에 고려할 수 있습니다. 대부분의 평범한 포함 관계에서는 멤버 합성이 의도를 더 쉽게 설명합니다.

빈 정책 타입을 기반으로 두는 공간 최적화도 가능한 구현 패턴이지만, 모든 컴파일러와 레이아웃에서 ‘정확히 몇 바이트 절약’이라고 단정하지 않습니다. C++20의 <code>[[no_unique_address]]</code> 같은 대안도 관련될 수 있습니다. 실제 표준 레이아웃 요구, 주소·정렬, ABI와 컴파일러 동작을 확인합니다. 이 실습 팩은 크기·성능 벤치마크를 실행한 것으로 표시하지 않습니다.

## 항목 40. 다중 상속의 필요와 비용

서로 다른 작은 인터페이스를 동시에 구현하는 용도는 유용할 수 있습니다. 반면 상태를 가진 여러 기반을 겹치면 이름 모호성, 기반 부분 중복, 초기화 책임, 포인터 조정, 가상 상속 구조가 복잡해집니다. 가상 상속은 가상 함수와 다른 기능이며 공유 기반 부분과 초기화 규칙을 다룹니다.

다이아몬드 구조에서 virtual 기반은 가장 파생된 클래스가 초기화한다는 점을 확인합니다. 모든 다중 상속 문제를 virtual 키워드 하나로 해결하지 않습니다. 서로 독립적인 기능이라면 합성과 인터페이스 분리를 먼저 비교하고, 실제 계층이 필요한 경우에는 생성·삭제·캐스팅 경로를 시험합니다.

## 사례: 게임 이펙트 시스템의 경계

이펙트 리소스를 만드는 Factory, 실행 중 상태를 가진 EffectInstance, 렌더 요청을 모으는 Renderer는 서로 다른 책임일 수 있습니다. 코드 재사용 때문에 모든 클래스를 하나의 거대한 기본 클래스에 묶기보다, 수명과 변경 이유를 나누는 것이 이 단원의 적용입니다. 이 사례는 설계 설명이며 특정 회사 엔진의 실제 구조를 분석한 결과가 아닙니다.

## 이해 확인

<toggle>
공통 구현이 있으니 상속으로 묶으면 항상 더 좋은가?

공통 코드를 재사용한다는 사실만으로 public 대체 계약이 성립하지 않습니다. 포함 관계와 독립적인 알고리즘 객체로도 재사용할 수 있습니다. 접근 권한, 소유권, 변경 축을 함께 봅니다.
</toggle>

<toggle>
virtual 함수가 호출되니 기본 인수도 동적으로 선택되는가?

아닙니다. 기본 인수는 정적 선언을, 함수 구현 선택은 동적 호출 규칙을 따릅니다. 실습에서 이 두 축이 만드는 20과 30의 차이를 확인합니다.
</toggle>
