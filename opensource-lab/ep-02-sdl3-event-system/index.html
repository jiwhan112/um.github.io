SDL3 이벤트 시스템: 키 입력 하나는 게임에 어떻게 도착할까?

윈도·입력·오디오의 플랫폼 차이를 숨기는 SDL에서, 이벤트는 실제로 어디에 저장되고 누가 꺼내는가? 공식 C/C++ 소스 파일의 함수 호출과 자료구조를 따라가는 분석입니다.

1. 1분 요약 — 꼭 기억할 4가지

PLATFORM LAYER운영체제별 코드는 SDL 안에 있다

Windows와 X11 등은 입력을 수집하는 방식이 다릅니다. SDL은 비디오 백엔드의 PumpEvents 함수 포인터를 통해 차이를 감춥니다.

EVENT DELIVERY입력은 큐에 넣고 나중에 꺼낸다

발생한 입력을 SDL_Event로 표현하고 SDL_PushEvent를 거쳐 큐에 넣습니다. 게임 루프는 SDL_PollEvent로 소비합니다.

DATA STRUCTURE큐는 단순한 고정 배열이 아니다

현재 소스는 이중 연결 리스트와 제거 노드 재사용 목록을 사용합니다. 큐 접근은 뮤텍스로 보호합니다.

INPUT SEMANTICS이벤트와 키 상태는 답하는 질문이 다르다

방금 눌렀나?는 이벤트, 지금 누르고 있나?는 키 상태 조회가 어울립니다. 빠른 누름과 떼기는 상태만으로 놓칠 수 있습니다.

분석의 관점

SDL은 씬 그래프·물리·애니메이션·게임플레이 로직을 모두 제공하는 완성형 게임 엔진이 아닙니다. 여러 플랫폼의 창, 입력, 오디오, 그래픽스 연결 등을 제공하는 기반 라이브러리입니다. 이 회차에서는 입력·이벤트의 내부 구조에 집중합니다.

2. 입력 한 번이 지나가는 길

키보드의 스페이스 키가 눌렸다는 상황을 생각해 봅니다. 특정 플랫폼의 구현은 서로 다르지만, 이번에 분석한 소스에서는 백엔드가 수집한 정보를 공통 키보드 처리 경로에 전달하고, 게임은 SDL 이벤트를 소비합니다.

수집SDL_PumpEvents

OS·디바이스의 새로운 상태를 읽어들입니다. Windows와 X11은 별도 구현을 가집니다.

저장SDL_PushEvent

이벤트 필터·감시자를 거쳐 큐에 복사합니다. 필터에 의해 제외될 수 있습니다.

소비SDL_PollEvent

큐에서 다음 이벤트를 꺼내 게임 루프에 전달합니다. 이벤트가 없으면 false를 반환합니다.

4. 내부 자료구조 — SDL_EventQ는 어떻게 구성되어 있을까?

“큐”라는 말만 보고 고정 길이 배열이나 단일 std::queue를 떠올리기 쉽습니다. 하지만 이번 소스의 SDL_EventQ는 head, tail, free 포인터를 가진 이중 연결 리스트를 사용합니다. 각 노드는 SDL_Event와 이전/다음 노드 포인터, 이벤트 소유의 임시 메모리 연결 정보를 갖습니다.

제거: SDL_CutEvent

prev/next 포인터를 고쳐 대기 목록에서 제거하고 노드를 free에 연결합니다. 제거 대상 노드를 이미 알고 있을 때 포인터 수정은 O(1)입니다. 노드를 찾는 비용은 별개입니다.

노드 분리 ↗

이벤트 유형을 조건으로 골라 꺼내는 SDL_PeepEventsInternal은 head부터 순회하므로 큐 길이가 Q라면 최악에는 O(Q)개 노드를 확인할 수 있습니다. 큐 접근은 뮤텍스로 보호됩니다. 단, 이것은 소스 구조를 바탕으로 한 복잡도 해석이지 실측 처리량이 아닙니다.

흥미로운 구현 세부

해당 커밋의 SDL_MAX_QUEUED_EVENTS는 65,535로 정의되어 무제한 큐 증가를 막습니다. 이 값은 현재 조사한 내부 구현 상수이며, 모든 버전에서 불변인 공개 API 계약은 아닙니다. 앱이 이벤트를 충분히 소비하지 않으면 SDL_PushEvent가 실패할 수 있습니다. 상수 정의 ↗

한 프레임에 PollEvent를 여러 번 호출하면 OS도 매번 읽을까?

코드를 보면 단순하지 않습니다. SDL_PollEvent는 타임아웃 0으로 처리하고, 내부에서는 SDL_EVENT_POLL_SENTINEL이라는 특별한 이벤트를 활용해 한 번의 폴링 순환 경계를 표현합니다. 매번 무조건 같은 비용으로 플랫폼 이벤트를 다시 수집한다고 단정할 수 없습니다. 이 로직은 내부 최적화 구현이므로 앱은 공개 API 의미에 의존해야 합니다.

5. 게임 입력 처리의 핵심: 발생한 사건 vs 현재 상태

📨 이벤트(Event)

질문: 무슨 일이 발생했나?

SDL_EVENT_KEY_DOWN, SDL_EVENT_KEY_UP은 눌림·떼어짐의 전이를 나타냅니다. 입력 발생 순간에 반응하는 동작, 예를 들어 단발성 메뉴 선택에 적합합니다.

이벤트 시퀀스반복 여부 확인

🎛️ 상태(State)

질문: 지금 무엇이 눌려 있나?

SDL_GetKeyboardState()는 SDL 내부의 스캔코드별 bool 배열을 가리키는 포인터를 반환합니다. 누르고 있는 동안 지속되는 이동 같은 처리를 판단할 때 유용합니다.

현재 값SDL_Scancode

키를 매우 빠르게 눌렀다가 다음 게임 루프에서 상태를 읽기 전에 떼었다면 상태 배열은 이미 false일 수 있습니다. 반면 큐에 남아 있는 KEY_DOWN/KEY_UP 이벤트는 각각 확인할 수 있습니다. 단, 이벤트도 필터링·큐 가득 참·소비 지연 등에 영향을 받으므로 모든 물리 입력이 반드시 보존된다고 가정해서는 안 됩니다.

6. C++11 + SDL3 최소 사용 예제

이 예제는 렌더러를 만들지 않고 창과 입력만 처리합니다. SPACE 최초 누름은 이벤트로 구분하고, LEFT 현재 눌림 상태의 변화는 키보드 상태 조회로 구분합니다. 반복 KEY_DOWN을 걸러내는 방식도 확인할 수 있습니다.

#include <SDL3/SDL.h>
#include <SDL3/SDL_main.h>

int main(int argc, char* argv[]) {
    (void)argc;
    (void)argv;

    if (!SDL_Init(SDL_INIT_VIDEO)) {
        SDL_Log("SDL_Init failed: %s", SDL_GetError());
        return 1;
    }

    SDL_Window* window = SDL_CreateWindow(
        "SDL3 Event Study", 640, 360, SDL_WINDOW_RESIZABLE);
    if (!window) {
        SDL_Log("Window failed: %s", SDL_GetError());
        SDL_Quit();
        return 1;
    }

    bool running = true;
    bool previousLeft = false;
    while (running) {
        SDL_Event event;
        while (SDL_PollEvent(&event)) {
            if (event.type == SDL_EVENT_QUIT) {
                running = false;
            } else if (event.type == SDL_EVENT_KEY_DOWN
                    && !event.key.repeat
                    && event.key.scancode == SDL_SCANCODE_SPACE) {
                SDL_Log("SPACE pressed once");
            }
        }

        const bool* keys = SDL_GetKeyboardState(nullptr);
        const bool left = keys[SDL_SCANCODE_LEFT];
        if (left != previousLeft) {
            SDL_Log("LEFT is %s", left ? "held" : "released");
            previousLeft = left;
        }

        SDL_Delay(16); // 예제용 단순 대기. 정밀 프레임 제한이 아님.
    }

    SDL_DestroyWindow(window);
    SDL_Quit();
    return 0;
}

SDL3 개발 라이브러리와 CMake 패키지 구성 파일이 설치되어 있어야 합니다. 환경에 따라 실행 파일 옆에 SDL3 동적 라이브러리가 필요할 수 있습니다. 예제의 빌드·실행은 이 문서 작성 과정에서 수행하지 않았습니다.

왜 스캔코드를 썼을까?

SDL_Scancode는 물리 키 위치 기준이고, SDL_Keycode는 키보드 레이아웃에서 해석된 키 의미에 가깝습니다. 어떤 키를 기준으로 입력을 설계할지에 따라 선택이 달라집니다.

왜 !event.key.repeat일까?

누른 상태에서 OS/키보드 반복에 따라 KEY_DOWN이 다시 발생할 수 있습니다. “누를 때 딱 한 번”의 동작을 위해서는 반복 여부를 구분하는 것이 안전합니다.

스레드 안전성을 어디까지 믿을 수 있나?

SDL_PushEvent는 스레드 안전한 API이지만 SDL_PollEvent와 SDL_PumpEvents는 메인 스레드에서 호출해야 합니다. 이벤트 필터/감시자는 호출 스레드가 고정되지 않을 수 있으므로 공유 자료를 다룰 때 동기화가 필요합니다. PollEvent 공식 문서 ↗ · PushEvent 공식 문서 ↗

애플리케이션 전용 이벤트를 만들 수 있나?

SDL_RegisterEvents()로 다른 코드와 충돌하지 않는 사용자 이벤트 타입을 확보할 수 있습니다. SDL_PushEvent는 SDL_Event 구조체를 큐에 복사하지만, 사용자 데이터 포인터가 가리키는 객체까지 깊은 복사하는 것은 아니므로 수명 관리에 주의해야 합니다.

SDL_PeepEvents와 SDL_PushEvent는 같은가?

둘 다 이벤트를 추가할 수 있지만, SDL_PushEvent는 이벤트 필터 및 감시자를 통과하며 SDL_PeepEvents(... SDL_ADDEVENT ...)는 이 과정을 건너뜁니다. 따라서 완전히 같은 의미의 호출이라고 생각하면 안 됩니다.

창 크기 조정 중 항상 프레임이 멈추지 않나?

플랫폼 특성상 Windows 등에서 창을 드래그하거나 크기 조정하는 동안 SDL_PollEvent 호출이 생각보다 오래 지연될 수 있다는 주의가 공식 API에 명시되어 있습니다. “무조건 즉시 반환”의 성능 보장으로 오해해서는 안 됩니다.

성능 분석의 한계

이 문서는 큐의 연결 방식과 함수 호출을 근거로 한 구조 분석입니다. 메모리 할당 횟수, CPU 사용률, 이벤트 지연, 멀티스레드 처리량은 측정하지 않았습니다. O(1)/O(Q) 표기는 특정 연산에 대한 알고리즘적 해석이며 시스템 전체의 성능 보장은 아닙니다.

9. 스스로 설명해 보는 핵심 질문

Q1. 키를 빠르게 누르고 떼면 SDL_GetKeyboardState만으로 두 동작을 모두 알 수 있을까?

일반적으로 그렇지 않습니다. 상태 배열은 현재 값만 나타내며, 누름과 떼어짐이 다음 확인 전에 모두 끝나면 false만 보일 수 있습니다. 이벤트를 통해 각각의 전이를 처리해야 합니다.

Q2. SDL_EventQ가 이중 연결 리스트를 선택해 얻는 이점은?

필터와 같은 로직에서 탐색 도중 임의 노드를 제거해야 할 때 prev/next가 있으므로 제거 대상 노드를 알고 있다면 연결만 수정하면 됩니다. 또한 tail로 삽입과 free 노드 재사용을 지원합니다.

Q3. 왜 SDL_PushEvent 성공 반환값을 확인해야 할까?

이벤트가 필터에 의해 거절되거나 큐가 가득 차거나 내부 오류가 나면 false가 될 수 있기 때문입니다. 사용자 이벤트를 이용한 작업 신호 전달이라면 특히 실패를 고려해야 합니다.

Q4. 이벤트 필터가 SDL_EVENT_KEY_DOWN을 제거하면 키 상태도 false가 되나?

그렇지 않습니다. 확인한 키보드 처리 코드에서 상태가 먼저 갱신되고, 그 뒤 큐로 보낼지 판단합니다. 필터는 전달을 제어하지 실제 키 상태 갱신을 되돌리는 것이 아닙니다.
